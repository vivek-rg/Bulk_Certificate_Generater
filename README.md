# Bulk Certificate Generator

A browser application and backend API for accepting bulk certificate requests, validating recipients, generating one PDF per recipient, and tracking every outcome.

## Browser application

Open **http://localhost:8000/** after starting the server. The application includes:

- Certificate title and date fields with a live preview of the shared design.
- Editable recipients, pagination for large lists, and CSV import with `name,email` headers. CSV files are read in the browser; imported recipients can be reviewed before submission.
- Automatic job progress updates, per-recipient results, and individual PDF downloads.
- Recent batches saved in this browser, plus a job ID lookup for opening other batches. Only job IDs and batch metadata are saved locally; recipient names and emails are not saved in browser storage.

Emails identify recipients in the database; the application does not send email. The interface uses plain HTML, CSS, and JavaScript served by FastAPI, so no separate frontend installation or build step is needed. Edit `app/web/` to change the interface. The backend API remains available at `/api/v1`, with developer documentation at `/docs`.

## Architecture

```text
Client → FastAPI → Generation Job → Background Processor → Certificate Service → ReportLab/PDF template → Local file storage
                              ↘ SQLAlchemy → SQLite or PostgreSQL
```

`generation_jobs` holds aggregate progress and lifecycle timestamps. `certificates` holds one independently updated record per recipient, including the generated certificate number, status, error, and file path. Each certificate references its job with a foreign key. UUIDs are used for API-facing job and certificate IDs; PDF certificate numbers are separate, human-readable identifiers.

The API validates the complete request before committing a job. It then commits the job and all pending certificate rows together and returns `202 Accepted`. FastAPI `BackgroundTasks` runs the processor after the response. Each worker invocation opens its own SQLAlchemy sessions; an atomic `PENDING → PROCESSING` update prevents duplicate claims. Each recipient is generated and committed separately, so a failure is recorded and the next recipient still runs. The final job becomes `COMPLETED`, `COMPLETED_WITH_ERRORS`, or `FAILED`.

### Why background processing?

Generating hundreds of PDFs inside the HTTP request would keep the request open, increase timeout risk, and leave the client without useful progress. The API validates and saves the job, returns `202 Accepted`, and then processes each recipient. The processor saves the certificate outcome and updates the job counters after each recipient. One bad PDF does not stop the rest of the batch.

The current assignment uses FastAPI `BackgroundTasks`, which runs in the API process and can be interrupted by a crash or deployment restart. It keeps the HTTP contract independent of the queue implementation. For durable processing or very large jobs, keep the endpoints and state model, move `process_generation_job` behind a queue adapter, and run workers with Celery or RQ.

```text
Current (implemented)
Client → FastAPI ─┬→ SQLAlchemy → SQLite / PostgreSQL
                 └→ BackgroundTasks → processor → ReportLab → local PDF files

Future scale-out (not implemented)
Client → FastAPI → Redis task queue → Worker 1 / Worker 2
                       │                 ├→ PostgreSQL job state
                       │                 └→ S3 or other object storage
                       └→ retry metadata / queue coordination
```

Redis is a possible queue and coordination layer; the database remains the durable source for job and certificate outcomes. Production deployments can replace local files with S3/object storage and SQLite with PostgreSQL.

## Certificate template and storage

The shared, recipient-independent background is [templates/certificate_template.pdf](templates/certificate_template.pdf), generated by [scripts/create_template.py](scripts/create_template.py). The service overlays the configured organization name, recipient, course/title, date, and unique certificate number using ReportLab, then merges the result with the background using pypdf. The output is landscape A4 and is saved under `generated/<job UUID>/<certificate UUID>.pdf`. Only the path and metadata are stored in the database.

To change the static design, edit `scripts/create_template.py` and regenerate the PDF with `python scripts/create_template.py`. Set `ORGANIZATION_NAME` to customize the organization at runtime.

## API

All application endpoints are under `/api/v1`.

| Method and path | Purpose |
| --- | --- |
| `GET /health` | Liveness check |
| `POST /certificate-jobs` | Validate and accept a bulk job (`202`) |
| `GET /certificate-jobs/{job_id}` | Read counts, state, and calculated progress |
| `GET /certificate-jobs/{job_id}/certificates?page=1&page_size=50` | List recipient results; page size is 1–200 |
| `GET /certificate-jobs/{job_id}/zip` | Download all completed certificates as a ZIP archive; returns `409` if not ready |
| `GET /certificates/{certificate_id}` | Download a completed PDF; returns `409` while it is not ready |

Unknown jobs and certificates return `404`; invalid UUIDs and request payloads return `422`. Certificate listing includes a download URL only after successful generation, along with any per-recipient error message.

Interactive API docs are available at `/docs`; alternative docs are at `/redoc`.

## Setup

Requires Python 3.11 or newer.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
uvicorn app.main:app --reload
```

On Linux/macOS, activate with `source .venv/bin/activate`. Then open <http://localhost:8000/> for the application or <http://localhost:8000/docs> for developer documentation.

By default, the database is `./certificates.db`, generated PDFs go to `./generated`, and the PDF background is `./templates/certificate_template.pdf`. The app creates its tables and storage directory at startup. PostgreSQL can be selected with `DATABASE_URL=postgresql+psycopg://user:password@localhost:5432/certificates` (the conventional `postgresql://` prefix is also supported). The app reads a local `.env` file if present; shell environment variables take precedence.

Optional container run:

```bash
docker compose up --build
```

## Example flow

Create a job (Bash / macOS / Linux):

```bash
curl -X POST http://localhost:8000/api/v1/certificate-jobs \
  -H 'Content-Type: application/json' \
  -d '{"certificate_title":"Python Programming Certification","certificate_date":"2026-10-07","recipients":[{"name":"Rahul Sharma","email":"rahul@example.com"},{"name":"Priya Kumar","email":"priya@example.com"}]}'
```

1. The client sends `POST /api/v1/certificate-jobs` with a bulk request, for example 500 recipients.
2. FastAPI validates the complete payload before writing anything.
3. One transaction creates the job and a pending certificate row for each recipient.
4. The API returns `202 Accepted` with the `job_id` and recipient count.
5. A background task claims the pending job and processes recipients independently.
6. The client polls `GET /api/v1/certificate-jobs/{job_id}` for counts and progress.
7. Progress is calculated from completed recipients and reaches 100% when all outcomes are recorded.
8. The client lists results with `GET /api/v1/certificate-jobs/{job_id}/certificates`; failed rows include an error message.
9. The client downloads each completed PDF from its `download_url`, for example `curl -OJ http://localhost:8000/api/v1/certificates/{certificate_id}`.

A failed PDF for one person does not block the other 499.

## Tests

```bash
pytest
```

Tests use an isolated SQLite database and temporary certificate storage. They cover accepted job creation and persistence, invalid inputs, successful PDF generation, counts and progress, independent per-recipient failure, listing, downloads, and missing/not-ready retrieval. Frontend route tests cover the application homepage, static asset delivery, and escaping the configured organization name.

## Design choices and limits

- Generating hundreds of PDFs inside the request would keep a connection open, make timeouts likely, and prevent clients from observing progress. The endpoint only validates, persists, and schedules work.
- Separate job and certificate rows make aggregate progress cheap to read while retaining each recipient's status, output path, and error.
- The processor claims only pending jobs and uses a fresh database session per task/recipient. A unique constraint protects certificate numbers. For stronger crash recovery, use leases/timeouts, retries, and a durable queue; the simple in-process background runner intentionally does not promise delivery across restarts.
- Local files are easy for development. Multiple production workers should use shared object storage such as S3, with authorization and signed-download URLs.
- Authentication and rate limiting are outside this assignment's core scope. Add identity/ownership checks before exposing the API to untrusted clients.
